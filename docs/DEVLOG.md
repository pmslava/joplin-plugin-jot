## 2026-10-11 — v0.1.0: the first release

Designed and built in one day, from xiaofeng's request in the Cockpit forum thread (post 19) and Slava's decision the same afternoon to make quick capture a plugin of its own rather than a Cockpit feature. The design is `docs/BRIEF-1.0-jot.md`. Five Opus workers built it in phases on top of Cockpit's build configuration, harness shape and e2e launcher and Harper's content-script shape: the scaffold (c70dfa1), the form in create mode with Cockpit's date picker behind a bell (80b672f), the highlighted-text route with the In this note choice (e81455f), the typed `++` trigger as a CodeMirror 6 content script (26fb008), and edit mode with the `jot.open` contract for other plugins (7864d9f). A review pass between them fixed a wrong-row pick in the suggestion lists, a lost notebook filter on a mouse click, Escape closing the whole form, Unicode tag titles and a stuck trigger on a note switch.

Slava's corrections from trying the first build: the notebook field became a combobox that opens on a click, the Due row moved last so the unfolded picker pushes nothing down, and "Replace with a link" became the first and default choice on both the selection and the trigger routes.

Verified at release: 110 harness checks and 23 Playwright cases green in the isolated Joplin 3.6.14 AppImage. Not verified: anything on Android, the Rich Text editor live, the trigger under Gboard.

Process: the first publish of a new npm package cannot go through trusted publishing, so 0.1.0 was published locally with a web login and the OIDC trusted publisher configured right after, as Cockpit's first publish was; `publish.yml` skips a version that is already on the registry, so the release workflow stays green.

## 2026-10-12 — v0.1.2: the selection guard

Slava reported that Jot sometimes put him in the new note after a plain Create. The cause is Joplin's, read in the 3.6.14 and 3.7.21 bundles and reproduced in the e2e app: every tag change (a tag created or attached dispatches TAG_UPDATE_ONE, a tag removed NOTE_TAG_REMOVE) makes `BaseApplication.refreshNotes` reload the note list and select a note again, the last one selected in that list, or its first note when the list keeps none. A smart filter such as All notes keeps none, so after a Jot create with a tag the refresh selects the new note, which sorts first. Separately, moving a listed note to another notebook makes the reducer select the note that took its place. Without tags, or in a notebook view, nothing moves, which is why it happened only sometimes.

A plugin cannot stop the refresh, and Joplin has no command that selects a note in place, so `src/form/selectionGuard.ts` holds the selected note and the Markdown editor's view (the content script's new `jot.getView` / `jot.setView` commands) before a tag write or a notebook move, watches the selection for two seconds after it, and when Joplin moved off the note opens it again (`openNote`, which also switches the note list to the note's notebook) and puts the scroll offset, caret and focus back, since Joplin keeps no scroll position per note. The selection route now writes its link before the tags, and the trigger route writes its tags after the answer, so a jump can never carry the edit into the new note. `e2e/selection-guard.spec.ts` shows Joplin jumping on its own and both Jot routes ending on the note being read; with the guard disabled the two Jot cases fail. Harness 117, e2e 26 (plus the on-demand showcase).

The same day, Ctrl+Shift+J sometimes opened Firefox's Browser Console: that is Firefox's own shortcut, pressed while Firefox had the keyboard focus; Jot never receives keys while another application is focused.

## 2026-10-12 — v0.2.0: issues 1 to 3 and a calmer form

Three requests from CJeffyB, who wants to retire Convert Text To New Note and a pair of note templates in Jot's favour. **Issue 1**: the Tags start with the tags of the note you are in (setting on by default). **Issue 2**: a back link to that note, with Copy Note ID's placeholders (`{note_link}`, `{note_title}`, `{note_id}`, `{note_type}`, `{notebook_name}`, `{notebook_path}`, `{notebook_id}`, forgiving names, unknown ones kept), default text `Parent {note_type}: {note_link}`, its own line first (default) or last with an empty line between it and the text; off by default, and the form's Back link row (Add / Don't add) starts on the setting. **Issue 3**: a notebook setting, The current notebook or any existing notebook (an inbox); a plugin's enum options are fixed at registration, but Joplin 3.7.21's `Setting.registerSetting` takes the same key again with new options and keeps the stored value, so the list is registered at startup and again whenever the form reads a changed notebook list.

The form, per Slava: two buttons (Create, Cancel), the old Create and open replaced by an **Open** row (No by default, In editor, New window; a setting `openAfterCreate` replaces `openTarget`), every selector one line of segments (Type, In this note with short labels and the full wording as tooltips, Back link, Open), a 440px column, one control height, a heading with a keyboard hint, and selected segments that change colour but never weight. Reading the form's lists now asks for 100 items a page instead of the data API's default 10, and the form's reads run in parallel.

Harness 125 (26 checks retargeted for the new markup, settings and buttons, each named in the commit; 8 new). E2E 30, including `e2e/requests.spec.ts`, which picks the inbox from the Settings dropdown as a user would; the README screenshots were recaptured with `SHOWCASE=1`.

After Slava's first try, two more fixes went in before the release: Enter with an empty Title keeps the form open and focuses the Title (Joplin's own Enter would have closed it with nothing created), and Enter outside a text input - after a date picked with the mouse, on a segment, with nothing focused - submits through the form's submit event, since Joplin submits on Enter only in a text input. The current note's tags end with a comma and a space. Harness 127, e2e 33.

## 2026-10-13 — v0.2.1: the form no longer shrinks on Android

Slava saw the form open at the right size on the Pixel and then grow narrower and narrower. Joplin mobile sizes a fit-to-content plugin dialog to its content's measured width, re-measured every 500 ms (`PluginDialogWebView.tsx`, `useDialogSize.ts`), and the webview inside the dialog is the dialog's own width; the mobile rule was `width: calc(100vw - 16px)`, so every measurement took 16px off. The width now comes from the screen, which the dialog cannot change (`jotMobileWidth`: 94% of `screen.width`, 240 to 440px), set in pixels by the mobile switch; the form's CSS has no viewport unit left. Desktop closes the same loop live, so `e2e/mobile-width.spec.ts` reproduces it there: with the old rule the dialog collapses to Joplin's 200px floor, with the fix it holds at 387px for a 412px screen. Harness 128, e2e 34. Confirmed on Slava's Pixel before the release.

## 2026-10-13 — v0.2.2: issues 4, 5 and 6

**Issue 4** (CJeffyB: the Tags line overflows with no sign of it). Not a bug by the usual rule - a one-line field scrolls sideways with the caret and shows no scrollbar - but 0.2.0 made it likelier, since the Tags now start full of the current note's tags, and a probe in the e2e app found a worse trap beside it: Tab into a prefilled one-line field selects everything, so the first keystroke replaced every inherited tag. Title and Tags are now textareas of one row that grow to three lines and then scroll (the scrollbar is the sign of more), with the caret at the end on Tab and where clicked on a click; Enter never makes a new line in them (they submit through the form's submit event, since Joplin submits on Enter only in a one-line input), and a pasted line break becomes a space. Nothing depends on the dialog's own size, so the growth cannot feed back the way the Android width did.

**Issue 5** (a default for In this note). Every selector now has its default in Settings and remembers nothing between opens: "In this note, for highlighted text" (replace, keep, after) and "In this note, for the typed trigger" (link, remove) replace the hidden per-device memory of the last choice, which 0.1 had instead.

Harness 127 (26 checks retargeted for the textareas and the settings, two memory checks rewritten as issue 5's); e2e 37 with `e2e/fields.spec.ts`; screenshots recaptured.

**Issue 6** (CJeffyB: a "copy the parent's tags" button). Issue 1's tags-on-by-default suited his notes from highlighted text and fought his quick reminders, and the button would have been one more control on a full form. The real split is how Jot was opened: a quick note (nothing highlighted: the shortcut, the menu, the toolbar) or a note from text in a note (highlighted text, the typed trigger). So the tags and the back link each became "Never / For notes from text in a note / Always" (`tagsFrom`, default for text; `backlinkFor`, default never), and the notebook got one setting per kind of note: "Notebook for quick notes" (the 0.2.0 key, `defaultNotebook`, so a chosen inbox is kept) and "Notebook for notes from text in a note" (`textNotebook`), both the current notebook by default. A first version had a single notebook plus a scope setting ("Use the Notebook setting for: quick notes only"); Slava found the interaction unreadable on the Settings screen - why would a note from text ignore the inbox? - so each kind says its notebook in its own label. 0.2.0's two switches stay registered, hidden, so a choice made in them carries over once (tags off becomes Never, a back link on becomes Always) and is then reset. Harness 129, e2e 37; screenshots recaptured.

The Type selector reads Note, To-do, the order of Cockpit's New note and New to-do buttons, and so does the What Jot creates setting; the default stays To-do. Harness 130.

## 2026-10-14 — unreleased: quicker to open

Slava timed the Jot button on Android at 3 to 4 seconds before the form appeared. On a phone every call from the plugin to Joplin is a round trip, and the open made many: the selection read, about ten settings reads, every notebook and every tag 100 a page, and on the first open the dialog's build (create, five scripts, the buttons). Now the settings come in one call (`joplin.settings.values`, read in the 3.7.21 bundle; declared in `api/JoplinSettings.d.ts`, whose typings predate it; an app without it reads them one by one), the notebook and tag lists come from a cache read at startup, after every form and after every sync (a notebook the form must start on that the cache lacks, or a cache with no notebook at all, makes the form read first - the e2e suite caught the second: a profile whose first notebook was made after startup was told there was none), and the create form's dialog is built in the background once the plugin has started. A test build shows the timings in the form's heading (`src/core/timing.ts`, `SHOW_OPEN_TIMINGS`, never committed on) to find what the phone still spends. Harness 134, e2e 37.

Slava's first timings from the Pixel: idle, 1.17 s, of which Jot's own work was 0.06 s and Android showing the dialog 1.11 s; just after a sync 5.1 s (a single settings call 2.9 s); during a sync 28 s (settings 12.5 s, the dialog's build, not yet done by the warm-up, 6 s). Joplin is busy then and every call waits its turn, so the open now makes fewer: the settings are kept in memory, forgotten when Joplin reports a change (it does so a second after the last one, `Setting.scheduleChangeEvent`, so a form opened within that second starts on the old values), and the selection and the current note are read together at the tap. The timing line now splits "show" into the webview starting and the form's own setup.

The second round of timings (Joplin mobile 3.7.8): idle 1.32 s, of which Joplin starting the dialog's webview was 1.21 s and the form's own setup 0.03 s; right after a sync 10.23 s (the note read at the tap 7.33 s, a database read of the whole note, queued behind the sync and behind Jot's own re-read of the lists after the previous form); during a sync 21.25 s (the lists 12.22 s, the dialog's build 4.68 s), on a tap that came while Jot's own start was still running - 26.6 s, fourteen calls one after another, the log said (`adb logcat`, tag ReactNativeJS, carries Joplin's log). And the first form changed size and shape while Slava was typing in it.

That last one is Joplin's dialog pipeline read in the 3.7.8 source: the markup is the page, the stylesheet and the scripts are added afterwards over the same bridge, and the dialog is shown at the size measured right then and measured again only every 500 ms - seconds apart while a sync keeps the bridge busy. So the form opened at its unstyled size (selector rows on two lines each, 440px wide on a narrower phone, then narrowed by the script) and changed under him. Now everything that decides the size is in the markup: form.css minified into a `<style>` at its top (webpack `asset/source`; no longer a dialog script), the narrow layout a `-mobile` class on the form, the phone's width a pixel rule made in the plugin from its own `screen.width` (the dialog's own width when there is none - a fixed point, nothing taken off), the controls sized for the font (`max(28px, 1.35em + 10px)`: 28px clipped a phone's 16px line), Title and Tags sized by CSS `field-sizing: content` (Chromium 123; the phone's WebView is Vanadium 155), the font fallbacks the themes' own (desktop 12px Roboto, mobile 16px; a 13px fallback made the desktop form shrink 2px when the theme came), and the script gives the Title the focus only when nothing has it. A new e2e spec, `e2e/first-paint.spec.ts`, watches the desktop dialog every animation frame from the open and finds one size from Joplin's first measurement on, and lays the markup out alone, without its scripts, at the same height.

And fewer waits. The start sends its calls in waves (the warm-up first and unawaited: the dialog's build as two waits instead of seven, the lists' read, the note followed; the four commands together; the section and the settings together, then ONE settings read for the form, the toolbar gate, the 0.2.0 switches and the stored lists). The lists are stored in a hidden setting (`listCache`, compact JSON, plugin settings are not synced) for the first form after a start, and a notebook picked from them is checked against the first fresh read before Create or Save (a message and the form again if it is gone). The note the editor holds is read ahead when the selection changes, without its body, and again a moment after it changes, so a tap needs no database read for it. The markup is sent with the open rather than awaited before it (Joplin applies both in the order sent). The lists' re-read after a form waits 4 s, so a second form opened right away does not queue behind it, and a tag Jot creates joins the cached list at once. Edit mode reads the note and its tags together.

A review of the change (five areas, each finding put to a skeptic) kept six. A notebook picked from the stored lists was checked by waiting for the whole fresh read, after the dialog had closed and before the note and the edit to the highlighted text - seconds in which a tap in the editor would move where the link lands; it is now one read of that notebook (gone: not found, or in the trash). A sync ending while a list read was out joined that read, taken before the sync wrote; it now gets a read of its own after it. The re-read after a form was dropped when an edit form was up as its timer fired; it now waits. Joplin reports a selection only when it changes after a plugin starts listening (one previous value per property, shared by all plugins), so the note already open at the start never got a record; it is asked once, as Cockpit does. The phone's width is capped at the dialog's own width (`min(440px, 100%)`, nothing taken off, so still a fixed point), for a window narrower than the screen. And the bell kept the browser's small control font, so on a phone it was 28px among 31.6px controls. Harness 145, e2e 38; the new first-paint spec, run against the previous commit, fails there (200x377, the unstyled form, then 440x330) and passes here (440x330 at once).

Slava's third round, on the build above: during a sync 4.88 s (was 21.25), right after one 3.37 s (was 10.23), idle 1.21 s (was 1.32); the note was kept every time, and the screen width the plugin sees matched the dialog's (412/412). What is left is Joplin's: its webview took 3.85, 2.34 and 1.11 s, and the selection read one bridge trip (about 1 s while busy). But on every open the form's text and buttons showed for up to a second with no background behind them, a mess over the note during the sync. Joplin mobile shows the page at once in a dialog still at its largest and at opacity 0.1 until its first measurement comes back, and the Android webview does not fade with its parent, so the form drew crisp at the top of a transparent dialog, then jumped into the centred, opaque one. Now the form is transparent on mobile until Joplin has sized the dialog to it (`showJotForm`: the page as wide and tall as the form, or its width changed at all; a keyboard changes only the height), its layout kept for the measurement; form.css shows it after 6 s should the script never run. The timing line gains a "sized" part and reads "Shown in". Harness 146, e2e 38.
